# Speed audit: PoB session / adapter / worker layer

Baseline: the 3,280 s stormbrand build in `build.prof` (5,554 worker round trips).
Since that profile `read_state` was fixed (1.68 s -> 42 ms per call, 655 real reads),
so the *current* build is ~2,210 s; percentages below are still of the 3,280 s
profile, as asked, with the post-fix share in brackets where it matters.

All "measured" numbers come from two probe programs run against
`tests/fixtures/tuadh_329/stormbrand.pob.txt` on this machine
(`scratchpad/probe_lua3.py`, `probe_lua4.py`, `probe_ipc.py`, `probe_item_trials.py`);
Lua-side numbers were taken **in-process** (`HeadlessLuaRuntime` driven directly,
no IPC), end-to-end numbers through a real `PobSession`. The machine was ~65% busy,
so every figure is a `min` of 3-6 interleaved repetitions, never a mean.

## 1. `set_skills` — 12% of the build spent reloading a build to change a gem

`PobSession.set_skills` (`session.py:226`) builds a complete skills payload and calls
`apply_skill_state`. The worker (`headless_runtime_worker.py:1924`) then: exports the
whole build (`build:SaveDB('code')`, 13.0 ms), parses it with ElementTree (1.0 ms),
throws away the `<Skills>` subtree and rebuilds it from the payload, serialises
(2.3 ms) and calls `load_reopen_source` -> `loadBuildFromXML(...)` + `runCallback('OnFrame')`
(**422 ms** for the load alone, 492-592 ms with the frame). Measured end-to-end in the
worker: **469 ms**; the profile's 815 ms average is the same thing on a larger generated
build plus the IPC and the Python payload build.

The whole reload exists only to make PoB re-read gem names. PoB's own path for that is
`SkillsTab:ProcessSocketGroup(socketGroup)` (`SkillsTab.lua:1134`), which is exactly what
`LoadSkill` calls after filling a `gemList` from XML attributes (`SkillsTab.lua:492`) —
the reload adds nothing except re-parsing every item, rebuilding the passive spec and
re-reading the config. I changed one support in place (`gemList[n].nameSpec = ...`,
clear `gemId`/`skillId`, `ProcessSocketGroup`, `buildFlag = true`, `OnFrame`): **62.8 ms**,
the exported `<Skills>` element **byte-identical** to the reload path's, and **0 of the 51
objective stat keys** differ. 63 ms is almost entirely the mandatory full recalc, which
the reload path pays too.

What an in-place writer must reproduce, because `set_skills` rewrites the *entire* skills
surface every call (`generator.py:418` passes main link + every extra group):

* per gem — `nameSpec`, `level`, `quality`, `enabled`, `enableGlobal1`, `enableGlobal2`,
  `count`, `skillPart`(+`Calcs`), `skillStageCount`(+`Calcs`), `skillMineCount`(+`Calcs`),
  `skillMinion`(+`Calcs`), `skillMinionItemSet`(+`Calcs`), `skillMinionSkill`(+`Calcs`)
  (worker `:1967-1992`); `gemId`/`skillId` must be cleared so `ProcessSocketGroup` re-resolves
  the name through `FindSkillGem`, which is the code path the XML route takes too;
* per socket group — `enabled`, `includeInFullDPS`, `groupCount` (omitted when 1 — D49),
  `mainActiveSkill`, `mainActiveSkillCalcs`, `label`, `slot`;
* per skill set — id and `title`, and the set list itself;
* tab settings (worker `:2275-2282`) — `sortGemsByDPS`, `sortGemsByDPSField`,
  `activeSkillSet`, `defaultGemQuality`, `defaultGemLevel`, `showLegacyGems`,
  `showSupportGemTypes`; and `build.mainSocketGroup` (written as `Build/@mainSocketGroup`).

Everything on that list lives on `build.skillsTab` / `build` and is settable from Lua.
The one thing the reload gives for free is PoB's own normalisation of the rest of the
build; the proof that it is not needed is the export diff, which is why the acceptance
test must be "the exported XML of the whole build is identical", not just `<Skills>`.

## 2. `set_config` — the same reload for a handful of input values

`apply_config_state` (`:2324`) is structurally identical to `apply_skill_state`: export,
rebuild `<Config>`, reload. **593 ms** in the worker, 922 ms in the profile (the session
layer adds a `config_inputs()` export on top, see 5). PoB already has the in-place
operation: `ConfigTab:RestoreUndoState` (`ConfigTab.lua:1194`) wipes `configSet.input`,
writes the new keys and calls `BuildModList()`. Doing that for both config sets plus a
recalc took **165.8 ms** and produced identical stats and an export carrying the new
input.

An incremental config write must preserve: the **two config sets** (Baseline and
Conditional — the worker writes both on every call and `snapshot_calc_packet` at `:4495`
evaluates both lanes), `activeConfigSetId` (switch through the existing
`_set_active_config_set`, `:4242`), and the three build-level attributes that do *not*
live in a config set — `bandit`, `pantheonMajorGod`, `pantheonMinorGod` (worker
`:2337-2339`). Numeric preservation stays where it is: `session.set_config` already
merges the existing non-boolean inputs before calling the adapter (`session.py:343-351`),
so the worker only has to write what it is given. `BuildModList()` must run for the set
that is active after the write; the inactive set's inputs are only read when
`snapshot_calc_packet` switches to it, which already forces a rebuild.

## 3. `mutate_nodes` — 140 ms because the path rebuild runs twice

`spec:AllocNode` ends with `self:BuildAllDependsAndPaths()` (`PassiveSpec.lua:799`) and
`spec:DeallocNode` does the same (`:818`). `_MUTATE_TREE_LUA` then calls
`spec:BuildAllDependsAndPaths()` again (worker `:1154`). Measured on one build state:
the rebuild is **39.3 ms**, a bare `DeallocNode` is **38.1 ms**, and the full
`mutate_tree_nodes` for the same single node is **80.0 ms** — the second rebuild is
essentially the whole difference. `build.itemsTab:UpdateSockets()` (`:1155`) is 0.004 ms
and `CountAllocNodes` 0.004 ms, so neither matters; there is no recalc in this action
(only `buildFlag = true`), which is why `stats()` right after a mutation costs ~100 ms
(profile: `tree_optimizer.current_score` 376 calls, 38.9 s) while a clean `stats()` costs
0.16-0.37 ms.

Dropping the trailing call is exact whenever at least one node was allocated or
deallocated, and when none was the call is a no-op anyway. The larger prize — running one
rebuild for a whole batch of adds and removes instead of one per node — is **not** exact:
`DeallocNode`'s cascade reads `node.depends`, which only the rebuild refreshes, so
removing k nodes without rebuilding between them can cascade differently. Do not take
that one without a cascade-equality test over random multi-node mutations.

## 4-5. `read_state` and `config_inputs` still round-trip the build XML

After the recent fix `snapshot_state` costs **28.0 ms** in the worker (26.2 ms
end-to-end), and **~26 ms of that is two `build:SaveDB('code')` calls**: one in
`_snapshot_rich_skill_state` (`:3636`, to learn the skill-set ids) and one in
`_snapshot_config_state` (`:3889`, which parses `<Config>` back out of the export).
Both read state that is sitting in `build.skillsTab.skillSets` and
`build.configTab.configSets`. The same applies to `PobSession.config_inputs`
(`session.py:285`), which exports the whole build and walks `<Config>` with ElementTree
to read the active set's inputs — 407 calls, 39 ms each, 15.8 s.

A landmine to keep in view: `_snapshot_rich_skill_state` still does **two full reloads
per extra skill set** (`:3654` and `:3658`, the restore). Generated builds have one skill
set, so this is dormant; a skeleton or fixture that grows a second set puts ~1 s back onto
every `read_state`, and `config_rules.build_text` calls `read_state` 707 times per build.

## 6. The cached-state `deepcopy`

`PobSession.read_state` returns `copy.deepcopy(self._state_cache)` (`session.py:407`) so
that callers cannot corrupt the cache. In the profile that deepcopy is the entire gap
between `session.read_state` (1,113.5 s) and `adapter.read_state` (1,098.8 s): **14.7 s
over 1,062 calls**, ~14 ms each on a 2.4 MB state payload (measured 1.9 ms on the 77 KiB
fixture state — the profiled builds carry a much bigger state). A `json.loads(json.dumps(...))`
round trip is typically 3-5x faster than `deepcopy` for this shape, and handing out the
cached object behind a read-only view costs nothing at all.

## 7. `trial_stats` fast — 40% of the build, and almost none of it is ours

One fast trial is one call of PoB's misc calculator: `calcs.initEnv` + `calcs.perform`
(+ `calcs.calcFullDPS` when asked). Measured on the fixture with the real 51-key
objective: **5.0-6.0 ms per trial** inside a batch, `calcFunc({}, false)` **5.83 ms**
standalone, of which `initEnv` alone is **2.34 ms (40%)**. Everything the worker adds on
top is noise: `pick()` over 51 keys is **0.004 ms** per trial, `json.encode` of a
400-result batch is **29 ms** (1.4% of that batch), the Python decode of the same 388 KiB
is 5.8 ms, and the whole IPC round trip is 0.10 ms. An item trial (`new('Item', raw)` +
`BuildAndParseRaw` + `repItem` override) is **6.0 ms** against 5.4 ms for a node trial, so
`loot_gear`'s 217 s is simply ~30,000 trials, not an item-parsing problem.
`GetMiscCalculator` is free (0.008 ms — `CalcsTab.lua:757` just unpacks a cached closure),
so batching more trials per round trip buys nothing either.

Two calc-level levers exist and only one is already taken. The FullDPS roll-up **is**
already conditional: the worker sets `use_full_dps` only when `"FullDPS"` is among the
keys (`:967-968`) and PoB honours it (`Calcs.lua:137`), worth 6.3 ms of 12.1 ms — that is
why a stormbrand trial costs 5-6 ms and a minion/totem build's 12-25 ms. The unused lever
is `calcs.perform(env, skipEHP)` (`CalcPerform.lua:1252, 3722`): patching it in cut a
trial from 5.83 to 5.00 ms, i.e. `buildDefenceEstimations` is **14%** of a trial. But the
rails objective floors the four `*MaximumHitTaken` stats (`rails.py:130`, D53) and those
come out of `buildDefenceEstimations`, so skipping it would change which trial wins — not
exact. The only place it is legitimate is `pipeline._slots_with_damage_headroom`
(`pipeline.py:768`), which builds a damage-only objective; that is 18 calls and 16 s, so
~2 s. Not worth a worker flag on its own.

## 8. `load_xml` as an undo

171 whole-build loads cost 129 s, and 127 of them are `pipeline._value_with_enabled`
restoring a build it changed one config value on (94.8 s), with `tree_optimizer._restore`
taking another 28 (22.2 s). Each is `loadBuildFromXML` at 422-522 ms plus the export that
preceded it. The decision is the optimizer's, but the primitive it needs belongs here: a
worker action that snapshots and restores just the surface the caller touched — the
config inputs (see 2) or the passive spec's `allocNodes` + `masterySelections` (PoB's own
`CreateUndoState`/`RestoreUndoState` on `PassiveSpec` and `ConfigTab` do exactly this).
Restoring a spec is one `BuildAllDependsAndPaths` (~39 ms) instead of a 500 ms reload.

## 10. Do not touch the protocol

The reader-thread-per-call design in `_readline_with_timeout`
(`headless_runtime_adapter.py:110`) creates 5,554 threads per build and the whole
parent-side machinery — `json.dumps` (0.45 s), `json.loads` (1.93 s),
`_parse_worker_message` (1.82 s), thread bootstrap (2.52 s), `_call_worker` (0.16 s) —
comes to about **7 s of 3,280 s (0.2%)**. Measured directly: an end-to-end `tree_light`
is 0.216 ms against 0.119 ms of Lua, and a one-key `read_stats` 0.162 ms against
0.065 ms, so the round trip itself is **~0.10 ms**. `_normalize_unified_state_payload`
(`:76`) does not even appear in the profile. Rewriting this layer (length-prefixed
frames, a persistent reader thread, msgpack, shared memory) would buy under half a
percent. The one reason to revisit it is correctness, not speed: on a timeout the reader
thread is abandoned holding `stdout`, which is why `_call_worker` kills the worker at
`:688-693`.
