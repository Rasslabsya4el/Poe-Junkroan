# Speed audit: the Lua side of a trial, a stats read, and PoB's own calculation

Measured 2026-09-18 on the pinned runtime (`var/cache/pob/v2.67.2/app`, LuaJIT 2.1.1784580905),
fixtures `tests/fixtures/tuadh_329/*`, through `HeadlessLuaRuntime` driven in-process so probe Lua
could be executed on the bridge. Timings use `QueryPerformanceCounter` through LuaJIT's ffi
(`os.clock` on this host has 1 ms granularity and is only used where a block is >10 ms).
Probe scripts: `scratchpad/probe_jit.py`, `probe2.py` … `probe9.py`. No repo file was changed.

Build-level percentages assume the numbers in D61: one build ≈ 123,000 trials (106,000 in the tree
stages, ~400 greedy steps × ~267 candidates), 61-69 min = 3,700-4,100 s wall.

Anatomy of one fast trial (stormbrand, no FullDPS, 6.07 ms, function-level instrumentation):
`initEnv` 2.94 ms (48 %) — of which `buildModListForNodeList` 0.89, `createActiveSkill`+`buildActiveSkillModList` 0.61 —

## Finding 1 — the FullDPS roll-up

`calcs.getMiscCalculator` builds a closure (`Calcs.lua:134`) that, per call, runs `calcs.initEnv` +
`calcs.perform` and then, `if (useFullDPS ~= false or build.viewMode == "TREE") and usedFullDPS`, the
whole `calcs.calcFullDPS` — which builds *another* env and performs *every* socket group flagged
`includeInFullDPS`, including the main skill that was just calculated. Our chunk already passes
`use_full_dps` correctly (true only when `"FullDPS"` is among the requested keys,
`headless_runtime_worker.py:967-968`), and `usedFullDPS` is false for a build with no flagged group —
which is why the fixtures split cleanly: 0 flagged groups → 5.9-12.6 ms with and without FullDPS
alike; flagged groups → 8.3→15.4 (hit_penance_brand), 7.8→16.6 (stormbrand), 9.0→17.2 (SRS),
7.6→27.3 (impale_ballista), 11.3→51.4 (toxic_rain), 34.8→97.4 (vd_spellslinger).

Note the second clause: if anything ever sets `build.viewMode = "TREE"`, every trial pays the
roll-up regardless of the flag. In our host `viewMode` is `"IMPORT"` (measured), so it never fires.

The shortcut is sound for the builds *we* generate because `PobSession.set_skills` flags exactly one
group (`session.py:252`, `"include_in_full_dps": True` on the "Main" group) and extra groups default
to false (`Skeleton.SocketGroup.include_in_full_dps = False`, `hypothesis.py:185`). The count PoB
multiplies by is the gem's own `count` attribute (`Calcs.lua:150-174`, `getActiveSkillCount` returns
`gemData.count or 1`), written from `Skeleton.gem_counts` (`skeleton.py:190`, D49/D57). Measured on
stormbrand: `FullDPS / TotalDPS = 2.000000` on every one of 40 node-removal trials, standard
deviation 0.000000, count 2 — and the induced ranking over the 40 trials is identical. For minion
skills the per-instance number is not in `env.player.output` at all (SRS: `FullDPS = 20.1413 ×
env.minion.output.TotalDPS`, constant; the 0.7 % over the gem count 20 is the ailment roll-up), so a
minion trial would have to build the env itself (`calcs.initEnv` + `calcs.perform`, the same cost as
`calcFunc` minus the roll-up) and read both outputs. The fixtures where the ratio is *not* constant
are exactly the ones with two or more flagged groups (absolution_minions, impale_ballista, toxic_rain,
cold_dot, winter_orb …) — authors' builds, not shapes our generator produces; a per-build guard
("the ratio was constant over the first N trials, else fall back to real FullDPS") keeps that honest.
The objective asks for FullDPS only when `mode == "minion"` or no mode is given and
`counts_instances` is true (`objective_select.py:44-60`), so the saving lands on minion / brand /
totem / corpse-fed builds and nowhere else.

## Finding 2 — `mutate_nodes` is three tree-wide path rebuilds

`PassiveSpec:AllocNode` ends with `self:BuildAllDependsAndPaths()` (`PassiveSpec.lua:799`) and so does
`DeallocNode` (`:818`); `_MUTATE_TREE_LUA` then calls it once more explicitly
(`headless_runtime_worker.py:1154`). Instrumenting the method and calling the worker action end to
end: remove 1 node = 112.4 ms wall of which 111.3 ms is 2 rebuilds; add 1 node = 84.3 ms / 2 rebuilds;
remove 3 = 147.1 ms / 4 rebuilds; add 3 = 151.6 ms / 4 rebuilds. Nothing else in the call is
measurable (`UpdateSockets` 0.05 ms, `CountAllocNodes` 0.14 ms). That is the 140 ms the docs record as
60 ms — it is not a recalc (the Lua only sets `build.buildFlag`; the recalc is paid by the next
reader), it is `BuildAllDependsAndPaths` walking all ~4,000 tree nodes, re-running `ReplaceNode` and
the jewel-radius checks and rebuilding every path (`PassiveSpec.lua:1098-1230+`). The exact, provable
win is dropping the trailing explicit call whenever an Alloc/Dealloc ran (it is idempotent and the
last one already did it): one rebuild instead of two on the common single-node mutate. Batching a
multi-node mutate into one rebuild is *not* exact — `DeallocNode`'s cascade reads `node.depends` and
`AllocNode` reads `node.path`, both products of the previous rebuild — so that one has to be proven
by tree equality, not assumed.

## Finding 3 — what a dirty recalc actually does

`build.buildFlag` set → the next `runCallback('OnFrame')` runs `Build.lua:1238-1249`:
`wipeGlobalCache()`, `skillsTab:UpdateSocketGroups()`, `calcsTab:BuildOutput()`, `RefreshStatList()`.
`BuildOutput` (`CalcsTab.lua:452-464`) is four full calculation passes: `calcs.buildOutput(MAIN)`,
`calcs.buildOutput(CALCS)`, `getNodeCalculator`, `getMiscCalculator` — 21 `initEnv` calls and 17
`perform` calls in one OnFrame (instrumented). Measured per step (5 reps): MAIN 60.3 ms with a cold
`GlobalCache`, CALCS 13.0, `getNodeCalculator` 12.2, `getMiscCalculator` 11.2, `RefreshStatList` 1.1,
the `finalModList` loop 0.8, `UpdateSocketGroups` 0.09, `wipeGlobalCache` 0.014; the whole thing 91.8
ms. Three of those are dead weight in our lane:

* `getNodeCalculator` (12.2 ms) — `CalcsTab:GetNodeCalculator` (`CalcsTab.lua:753`) has **no caller
  anywhere** in `vendor/pob/source/src`; `PowerBuilder` uses `GetMiscCalculator`. Pure waste.
* the CALCS lane (13.0 ms) — `calcsOutput` is read only by `read_calc_snapshot`
  (`headless_runtime_worker.py:4440`), i.e. by `calc(lane)` for reports, never in a loop.
* the MAIN cost-warning loop (~48 ms) — `calcs.buildOutput` in MAIN mode calls
  `calcs.buildActiveSkill` for every active skill missing from the just-wiped `GlobalCache`
  (`Calcs.lua:500-512`; 9 calls, 51.5 ms instrumented) purely to fill `ManaCostWarning` /
  `*WarningList`, which nothing in `optimizer/` or `search/` reads. The same `buildOutput(MAIN)` with
  a warm cache is 12.4 ms.

The clean way to take it is an override of `CalcsTabClass:BuildOutput` in `headless_wrapper.lua`
(MAIN + `getMiscCalculator`, CALCS built lazily when the snapshot asks) — the wrapper is ours, the
vendor tree stays untouched. The cost-warning loop is the risky third: `GlobalCache` is also read by
`CalcPerform.lua:32-38` for other skills' values, so skipping it must be proven by the existing
34-fixture stats-equality harness before it is believed.

## Finding 5 — the JIT question, answered

`headless_wrapper.lua:268` does `dofile(Launch.lua)`, and `Launch.lua:17` is top-level, so
`jit.opt.start('maxtrace=4000','maxmcode=8192')` runs during bootstrap; `luaL_openlibs`
(`headless_runtime_worker.py:1207`) opens LuaJIT's `jit` library, and a bad parameter there would
raise and abort the boot. Direct read-back: `jit.status()` → `true`, `jit.version` → `LuaJIT
2.1.1784580905`, and `jit.util.traceinfo` counts **1,402-1,566 live traces**, which cannot exist under
the default cap of 1,000. A/B with warm-up and 30 timed trials, three repetitions: pinned settings
5.22 / 5.41 / 5.38 ms, LuaJIT defaults 12.38 / 13.78 / 12.73 ms — and under the defaults the live
trace count collapses to 158-620 between blocks, i.e. the cache is being flushed wholesale. So
trace-cache thrashing, if the settings were ever lost, would cost **+140 % on every trial** (~2.4×),
which on a 123,000-trial build is over an hour. Two corollaries worth keeping: with the JIT switched
off entirely the trial costs 5.71 ms — *slower than the interpreter by only 8 %* — so PoB's calc is
bound by allocation and table churn, not by hot numeric loops, and no JIT tuning will buy anything;
and nothing in our code should ever call `jit.flush()` (a flushed cache costs ~50 % more for the next
few hundred trials: 10.7 ms vs 7.1 ms measured).

There is no worker action that executes arbitrary Lua (the dispatcher at
`headless_runtime_worker.py:5205-5341` is a closed list), which is correct and should stay that way.
The Lua chunks reach the runtime as Python string tuples joined and passed to
`LuaJITBridge.execute` → `luaL_loadstring` + `lua_pcall` (`:1220-1236`). For a one-line probe the
exact place is a new `if action == "eval_lua": _success(result={"ret": runtime._bridge.execute(
command["code"], nret=1)[0]})` beside the other actions at `headless_runtime_worker.py:5247` — but it
is not needed: constructing `HeadlessLuaRuntime(runtime_root=…, session_root=…, wrapper_path=…)` in a
throw-away Python process (after setting `POB_RUNTIME_ROOT` / `POB_HEADLESS_USER_PATH` /
`POB_HEADLESS_WORKDIR`) gives the same access, which is how every number above was taken.

## Finding 6 — the output side needs nothing

The trial chunk encodes only the requested keys: `pick(out)` iterates `payload.keys`
(`headless_runtime_worker.py:975-979`), never the whole `output` table. Building 400 such result
tables costs 0.29-0.38 ms and `json.encode` of the batch 4.86 ms (90.8 KB) — 0.2 % of the 2,400 ms of
calc such a batch represents. Decoding the incoming payload is 1.84 ms for 400 trials (24.5 KB), and
compiling the freshly-concatenated chunk is 0.04-0.15 ms per call. For scale: the full `mainOutput`
has 747 scalar entries and encodes in 2.1 ms — encoding it per trial instead of the keys would be
~35 % of a trial, so the current design is the right one and there is nothing to win here.
`read_stats` itself is the same shape and only pays `runCallback('OnFrame')` when `build.buildFlag`
is set (a clean OnFrame is 2.1-2.4 ms, a dirty one 92 ms — finding 3).
