## Decision

[DERIVED] Do not put Jev between PoB and a build number.

[DERIVED] A bounded pilot is defensible for ambiguous worker/log-state triage as a secondary judge, and a separate source-grounded text-classification pilot is defensible for mechanics lines only if its high-confidence lane is quarantine/review rather than permission to turn a conservative PoB input on.

[DERIVED] Do not integrate Jev for package proposal, passive-node selection, item-affix selection, config toggles, or screen ranking now.

[DERIVED] First repair and extend the deterministic PoB-derived stat graph and use PoB's exact 7 ms probes for package discovery.

## What Jev actually exposes

### API shape

[SOURCE] The model page documents Jev 1.13 as model ID \`jev-1.13.0\`, with aliases \`jev-latest\` and \`jev-preview\`; it states that aliases can move and that the response reports the versioned model.

[SOURCE] The model page lists price as $42 per billion input tokens ($0.042 per million), zero charge for output tokens, a 250,000-token-per-second limit, a 1,200-request-per-minute limit, a 64k total context, and a 32k state-plus-longest-question limit.

[SOURCE] The model page says input is text only and that images, audio, and video must be converted to text or structured fields.

[SOURCE] The model page warns that rate limits are dynamically adjusted and can change without notice.

[SOURCE] The API page documents POST \`https://api.typesafe.ai/v1/systemone\` with Bearer authentication and a body containing \`state\`, \`model\`, and a map of named \`questions\`.

[SOURCE] The API page says state can be a string, object, or array and that a question key is not sent to the underlying model.

[SOURCE] The API defines three question types: Noul, Choice, and Score.

[SOURCE] Noul returns a yes probability in \`noul\`; the documented Noul response does not include a separate confidence field.

[SOURCE] Choice returns one selected option and a full probability distribution over the supplied options, with confidence.

[SOURCE] Score returns a probability-weighted score over an ordered list of two to ten described levels, with probabilities, legend, and confidence.

[SOURCE] The API allows at most 255 Choice options.

[SOURCE] The TypeSafe Python SDK documentation provides synchronous and asynchronous clients, and the SDK's package metadata declares Python >=3.10 and Windows support.

[SOURCE] The SDK retry documentation sets a default RetryPolicy of two retries after the initial attempt, with backoff and retryable HTTP statuses including 429 and 500–599.

[DERIVED] A client integration on this Windows Python 3.12 repository is technically plausible, but it must pin \`jev-1.13.0\`, validate every response locally, log input tokens and model version, and budget for retries.

[UNVERIFIED] I found no public separate Batch API, batch discount, guaranteed p95 latency, account-specific quota, or contractual determinism setting.

### Confidence, probability, determinism

[SOURCE] TypeSafe's confidence documentation says confidence is a statistic computed from the returned probability distribution and gives the full distribution so a caller can choose another measure.

[SOURCE] The same page's interactive example uses an approximate three-option formula, \`(3 × largest probability − 1) / 2\`, rather than presenting that widget as a formal server contract.

[SOURCE] The Jev 1.13 jaggedness page says Jev can be literal, unreliable at math and counting, weak on dates and indirection, degraded by irrelevant context, vulnerable to adversarial content, confused by contradictory instructions, unable to guarantee structural invariants between separately asked questions, and unsuitable for generation.

[SOURCE] The jaggedness page says: "Jev is not a calculator."

[SOURCE] The jaggedness page says Score levels are weak for numerical calibration and that arithmetic should stay in code.

[SOURCE] TypeSafe's FAQ says: "Determinism means returning the same result for an identical input. This is less valuable than consistency. We define consistency as making similar decisions when the meaning stays similar. Jev is designed for consistency."

[SOURCE] TypeSafe's own consistency cookbook reports 90.8% raw agreement on its repeated Choice experiment and 99.2% policy agreement after a 0.60 top-probability threshold, while also stating: "These percentages measure repeatability only."

[SOURCE] The same cookbook reports that 25.8% of answers were uncertain and 74.2% automatic under that illustrative policy.

[DERIVED] Confidence is not an independent verifier and is not a correctness certificate.

[DERIVED] A high-confidence PoE verdict can still be wrong, especially under a domain or patch shift, so a high-confidence result can only route a case to a pre-approved action.

[DERIVED] Noul thresholds, Choice thresholds, and Score thresholds must be calibrated separately on labels from this repository.

### Calibration evidence

[SOURCE] TypeSafe's launch evaluation covers security incidents, agent-trace observability, invoice processing, and customer service, and compares against a reference made by averaging GPT-6 Astra and Claude Fable 5.1 at high thinking.

[SOURCE] The launch evaluation page does not provide a reliability diagram, ECE, Brier score, PoE-domain calibration, or OOD calibration result.

[SOURCE] TypeSafe's classification-confidence cookbook reports a 60-document example in which the confidence-0.9 group was right 90% of the time and the other group 40% of the time; the document says the labels are self-reported industry codes.

[SOURCE] The independent TrueStandard article by Arun Agrahri, dated 18 September 2026, reports a 108-claim grounding test across six source passages: Jev accuracy 96.3%, Brier 0.0331, ECE 0.0660; Gemini Flash Lite accuracy 94.4%, Brier 0.0369, ECE 0.0611; Claude Haiku accuracy 93.5%, Brier 0.0547, ECE 0.0669.

[SOURCE] The independent article says it used 56 supported and 52 unsupported claims, one run per model, and that its conclusion changed as the test grew from 22 to 72 to 108 claims and as the prompt was corrected.

[SOURCE] The same article says the hard near-miss tier was where Jev separated, with reported accuracy of 91.7% versus 83.3% and 80.6% for the two chat models.

[SOURCE] The independent article does not provide a machine-readable complete prediction file, exact ECE bin definitions, confidence intervals, or a PoE test.

[DERIVED] The independent result is useful evidence that Jev may be strong on source-grounded near-miss classification, but it is not evidence that Jev can safely decide whether a PoE mechanic is proven.

[DERIVED] The independent ECE values are close enough that the published sample cannot support a claim that Jev is uniquely calibrated.

[UNVERIFIED] I found no reliability diagram, ECE, Brier, risk-coverage, or abstention study on PoE 3.29 item text, gem text, proxy delivery, charge generation, or config proofs.

### 1. Mechanics text triage

[SOURCE] The brief names \`src/junkroan/optimizer/config_rules.py\`, D77, D75, D80, parsed mods, player/proxy/minion subjects, and the risk that a wrong "proven" toggle inflates a build number.

## Proposed pilot protocols

### Pilot A: mechanics review router

[DERIVED] Freeze a versioned rubric and send only a parsed line, PoB mod tags, gem tags, actor, and recursive preconditions.

[DERIVED] Use the existing parser and manually adjudicated rows as labels, with all rows from one reference/build family held out together.

[DERIVED] Compare Jev Choice, current deterministic rules, and a simple always-review baseline.

[DERIVED] Report dangerous false-proven rate, per-class recall, coverage, ECE, Brier, and a reliability plot.

[DERIVED] Stop the pilot from becoming production if any high-confidence threshold has a false-proven row on the held-out set.

[DERIVED] Budget $0.25 total for prompts, retries, and a second rubric revision, which is 5% of the stated $5 balance.

### Pilot B: worker/log fallback

[DERIVED] Build a replay harness around the stored \`.out\` tails and labels from \`report: present/MISSING\`, completion reasons, report files, and provider-error markers.

[DERIVED] Call Jev only on rule-ambiguous rows and include a \`needs_review\` option.

[DERIVED] Measure exact state accuracy, false healthy, false missing, outage recall, calibration, abstention, and added latency.

[DERIVED] Require Jev to beat the existing rule system on ambiguous rows without changing any known-correct state and without suppressing a continuation.

[DERIVED] Budget $0.10 for 10,000 ambiguous 2,000-token calls, leaving most of the $5 balance untouched.

### Pilot C: PoE-domain calibration before any mechanics authority

[DERIVED] Create at least 500 independently adjudicated items from D75–D80 and parser/audit disagreement rows, with positive and negative cases balanced by actor and condition.

[DERIVED] Use a fresh league/mechanic split and preserve all probabilities, confidence, model version, prompt hash, input hash, and token usage.

[DERIVED] Publish ECE, Brier, reliability bins, risk-coverage, and dangerous-error counts with bootstrap intervals.

[DERIVED] Do not call any threshold “safe” until the high-confidence lane passes the owner-set false-proven bound on the held-out split.

[DERIVED] This pilot is a prerequisite to any future consideration of Jev for mechanics triage; it is not a prerequisite for the worker/log pilot.

## What would change the verdict?

[DERIVED] A future Jev integration would require a pinned API version, confirmed balance/expiry/auto-refill settings, a local response validator, repository-domain calibration, a held-out dangerous-error bar, and a fallback to current deterministic rules.

[DERIVED] The package-proposal verdict would change only if a deterministic PoB graph cannot enumerate a demonstrably large residual space and a Jev prior improves recall of full-PoB winners at the same exploration budget without putting Jev in the acceptance path.

[DERIVED] The screen-ordering verdict would change if at least 30 paired screen/full labels show a stable winner-recall gain over no prior and random forest, with an exploration quota and no material loss on held-out archetypes.

[DERIVED] The mechanics verdict would change if a domain-held-out test shows near-zero false-proven rate in the high-confidence lane, useful coverage, and calibration that survives a new PoB/league corpus.

[DERIVED] The data-handling verdict would change if the account has confirmed zero-data-retention or a redaction-safe enterprise policy and the user explicitly accepts transmitting those selected text windows.

## Final three-sentence verdict

[DERIVED] Jev is not worth an afternoon of integration into the build optimizer now because PoB is exact at 7 ms, the repository's package graph is still repairable deterministically, and Jev has no demonstrated PoE-domain calibration.

[DERIVED] Jev may be worth a small later pilot for worker/log triage and source-grounded mechanics review, where $5 covers thousands of bounded calls and the deterministic system remains the authority.

[DERIVED] I would change that verdict after a held-out PoE calibration study and a winner-recall experiment show that Jev improves coverage or review cost without enabling a wrong conservative config, dropping a full-depth winner, or entering the path from candidate text to PoB build number.
